# تجهيز قاعدة مندوب على Supabase

تم تنزيل المشروع من `Fadysamy9/tayson-logistics` عند commit `6984979` ومراجعة هيكل قاعدة البيانات، طبقة الاتصال، الدخول والصلاحيات، التثبيت، الملفات، النسخ الاحتياطي وواجهة API.

التطبيق يستخدم React/Vite/Tailwind للواجهة وExpress/PostgreSQL للخادم. رُبط بمشروع mandob عبر Session pooler مع تحقق شهادة TLS. توجد لوحة إدارة وبوابة مناديب وموقع عام.

## الملفات

- `schema.sql`: 64 جدولًا و730 عمودًا و40 علاقة خارجية و69 فهرسًا إضافيًا، محوّلة من `server/src/schema.sql` الذي يستخدمه التطبيق.
- `seed.sql`: 112 إعدادًا، 5 أدوار، 807 صلاحية موزعة على الأدوار، 25 مدينة و17 قالب بريد. يمكن إعادة تشغيله دون تكرار البيانات أو استبدال إعدادات موجودة.
- `verify.sql`: فحص قراءة فقط بعد تطبيق الملفات على المشروع المختار.
- `manifest.json`: أسماء الجداول والأعمدة والأعداد المتوقعة.
- `validation.json`: نتائج الاختبار المحلي على PostgreSQL داخل PGlite.
- `generate.mjs`: إعادة توليد الملفات من تعريفات المشروع باستخدام Node 24 أو أحدث.
- `validate.mjs`: اختبار التنفيذ والقيود والبيانات الأساسية والصلاحيات محليًا.

**لا توجد بيانات تشغيل حقيقية أو نسخة MySQL تحتوي على سجلات داخل الريبو.** لو فيه نظام شغال بالفعل، نحتاج تصديرًا منفصلًا لبياناته وملفاته. لا يوجد حساب مدير أو كلمة مرور افتراضية في هذه الحزمة.

## التطبيق على مشروع Supabase

تم تطبيق `schema.sql` ثم `seed.sql` على مشروع **mandob** بالمرجع `mzsjtckqoqjinsjafnfb` عبر SQL Editor بعد التأكد من خلو schema `public` من الجداول. نجحت اختبارات التحقق الـ13 على المشروع الحقيقي: 64 جدولًا، 730 عمودًا، 40 علاقة، RLS على كل الجداول، وجميع أعداد البيانات الأساسية مطابقة. امتيازات الجداول وsequences لأدوار المتصفح تساوي صفرًا. النتيجة محفوظة في `deployment.json` ولقطة `deployment-proof.png`، واستعلام التحقق في `deployment-verification.sql`.

أُنشئ حساب المدير `miza`، واكتمل التثبيت (`system.installed=1`). بيانات الدخول محفوظة محليًا في `server/data/first-login.txt`، ومستبعدة من Git. الإيميل الأول `miza@mandob.local` placeholder محلي يمكن تغييره من الملف الشخصي. تقرير `application-verification.json` يسجل دخول الحساب وقراءة عشرة أقسام وفحوص القاعدة الحية بعد ربط التطبيق. `deployment.json` يوثق مرحلة إنشاء الجداول السابقة قبل إنشاء الحساب.

الخطوات التالية مرجع لإعادة التجهيز على وجهة جديدة؛ لا تعِد تشغيل `schema.sql` على مشروع mandob الذي تم تجهيزه.

1. اختر مشروعًا جديدًا أو قاعدة لا تحتوي على أي من جداول مندوب. ملف `schema.sql` مخصص للإنشاء الأول، وسيفشل داخل transaction إذا وجد جدول بنفس الاسم؛ لا يحذف أو يستبدل جدولًا موجودًا.
2. افتح SQL Editor وشغّل `schema.sql` كاملًا.
3. شغّل `seed.sql` ثم `rls.sql` كاملين.
4. شغّل `verify.sql`. راجع أسماء الجداول والأعداد وعمود RLS والامتيازات.
5. عند اعتماد المشروع، سجّل هذه التغييرات في سير migrations الخاص به. هذه الملفات standalone SQL وليست سجل migrations منشأ بواسطة Supabase CLI.

لا تشغّل SQL الخاص بـMySQL الموجود في `database/schema.sql` أو `server/src/schema.sql` على Supabase مباشرة.

## ما تغير في التحويل

- `AUTO_INCREMENT` أصبح `GENERATED BY DEFAULT AS IDENTITY` مع الاحتفاظ بأنواع الأرقام الحالية لتسهيل نقل العلاقات. عند استيراد IDs صراحةً لاحقًا، يجب ضبط sequences بعد الاستيراد وقبل تشغيل التطبيق.
- `DATETIME` أصبح `TIMESTAMPTZ`. التطبيق الأصلي يخزن التوقيت بـUTC؛ ملفات الإنشاء والتعبئة تستخدم UTC أيضًا. يلزم تفسير تواريخ أي تصدير قديم على أنها UTC.
- `JSON` أصبح `JSONB`، و`MEDIUMTEXT` أصبح `TEXT`، والقيم المالية بقيت decimal بدقة ثابتة.
- `ENUM` أصبح نصًا مع `CHECK` للقيم المسموحة.
- أعمدة `TINYINT(1)` بقيت أرقامًا 0/1 باستخدام `SMALLINT` و`CHECK` لتسهيل التوافق مع قيم الخادم الحالي؛ لم تتحول إلى boolean.
- فهارس MySQL التي تستخدم أول 150 أو 200 حرف أصبحت فهارس expression على `left(...)`. روابط الحذف `CASCADE` الموجودة محفوظة، وأضيفت فهارس للعلاقات التي لا يغطيها فهرس يبدأ بنفس العمود.
- لم تُحاكَ collation الخاصة بـMySQL (`utf8mb4_0900_ai_ci`). المقارنة والبحث والتفرد في PostgreSQL قد تختلف في حالة الحروف والتشكيل. يجب اعتماد قواعد تطبيع البريد واسم المستخدم والبحث العربي قبل ربط التطبيق أو استيراد بيانات فعلية.

## الوصول والصلاحيات

فُعّل RLS على الجداول الـ64 وسُحبت امتيازات الجداول وsequences من `anon` و`authenticated` و`PUBLIC`. لا توجد سياسات تسمح بالوصول المباشر من المتصفح حتى الآن. هذا مقصود في مرحلة التجهيز لأن التطبيق يستخدم sessions وصلاحيات داخل Express، ومعرّفات موظفين ومناديب رقمية، وليس Supabase Auth.

الطلبات تستخدم اتصالاً منفصلاً بحساب `mandoob_runtime` (LOGIN, NOINHERIT, NOBYPASSRLS) لا يستطيع SET ROLE postgres. كلمة المرور عشوائية في `.env` فقط باسم `DATABASE_APP_URL`؛ اتصال `DATABASE_URL` خاص بالعمليات الداخلية.

طلب الموظف أو المندوب المصادق عليه يستخدم دور PostgreSQL `mandoob_request` غير قابل للدخول وبدون BYPASSRLS، عبر SET LOCAL داخل transaction. يحدد الخادم الهوية من الجلسة المتحقق منها، وليس من جسم الطلب. سياق الهوية والدور يزول عند COMMIT/ROLLBACK، ويُمنع الوصول دون سياق.

سياسات المندوب تقيد صفوفه وطلبات التغيير والإجازات والماليات والرسائل ومرفقاتها، وتخفي الملاحظات الداخلية. تُمنع الكتابة لصفوف مندوب آخر وإعادة إسناد ملكية الطلب. المناديب لا يصلون لجداول الموظفين أو الأسرار. صلاحيات أقسام الموظفين تُفرض بواسطة `can()` في Express وتُقرأ في كل طلب؛ سياسة staff في PostgreSQL تسمح للموظف المصادق عليه بصفوف النظام، ولا تعيد تنفيذ مصفوفة الأقسام في SQL.

تسجيل الدخول والإعدادات الداخلية والتدقيق وتسليم البريد والإشعارات والمهام المجدولة تستخدم اتصال postgres خاصاً بالخادم، كعمليات موثوقة محددة. بيانات الاتصال لا تصل للمتصفح. لا تفتح صلاحيات Data API أو تنقل استعلامات المتصفح مباشرة إلى Supabase دون إعادة تصميم المصادقة.

الدخول للمندوب برقم فقط أُلغي؛ الإدارة تعين كلمة مرور من بطاقة حساب المندوب، وإعادة التعيين تنهي الجلسات السابقة. الملفات المؤقتة لا يقرأها أو يحذفها أو يعتمدها إلا صاحبها.

احتُفظ بـExpress وبجلسات الموظفين والمناديب الحالية، مع PostgreSQL على الخادم. لا تستخدم شرط `auth.uid() = user_id` مع المعرفات الرقمية الحالية دون إضافة ربط صريح. بيانات `users.password_hash` والجلسات والمفاتيح تظل خاصة بالخادم.

راجع [دليل RLS](https://supabase.com/docs/guides/database/postgres/row-level-security) و[اتصال PostgreSQL](https://supabase.com/docs/guides/database/connecting-to-postgres).

## ربط التطبيق وتشغيله

- استُبدل `mysql2` بـ`pg`، مع transactions ومعالجة التواريخ والأرقام وأخطاء PostgreSQL. `server/src/sql.ts` يترجم قوالب الاستعلامات القديمة ويُرسل جميع القيم كمعاملات منفصلة.
- التثبيت يستخدم PostgreSQL، ويتجنب إعادة إنشاء الجداول الموجودة. تحديث الإعدادات والقوالب يتم دون استبدال قيم المستخدم.
- الاستعادة تعمل داخل transaction بترتيب العلاقات وتضبط identity sequences. لا تستخدم `FOREIGN_KEY_CHECKS`.
- شغّل `Start-Mandoob.ps1` من PowerShell. التطبيق المحلي على `http://127.0.0.1:4000/admin/login`، ويحتاج الاتصال بالإنترنت لقاعدة Supabase.
- ملفات المرفقات والمفاتيح والنسخ الاحتياطية تظل في `server/data/`. احتفظ بهذا المجلد مع نسخة القاعدة.
- البريد يتطلب إعداد SMTP فعلي، ومزامنة هنجرستيشن تتطلب توصيل الإضافة والحساب. الوظائف المجدولة تعمل داخل عملية Express.
- اختبارات API الشاملة تعمل على PGlite محليًا عبر `server/test/local-postgres-server.ts` ثم `node server/test/smoke.mjs http://localhost:4200`. اختبار Supabase يستخدم schema اختبار منفصلًا وملفات منفصلة؛ لا تشغّله على بيانات العمل.

## نتيجة الاختبار

نجح تنفيذ schema والتعبئة مرتين على PostgreSQL محلي عبر PGlite. تحقق الاختبار من كل أسماء الأعمدة والعلاقات، RLS وامتيازات المتصفح، رفض القيم غير المسموحة والعلاقات غير الصالحة، حذف CASCADE، تفرد بادئات النصوص، decimal وJSONB. تحقق أيضًا من منع قراءة الصفوف عبر RLS حتى عند إضافة امتياز SELECT مؤقت بالخطأ.

نجح اختبار API الشامل على PostgreSQL المحلي **وعلى Supabase الفعلي داخل schema اختبار منفصل**، بما يشمل الدخول والصلاحيات والمركبات والمناديب والتجديدات والإجازات والسلف والتقارير والاستيراد والنسخ الاحتياطي والاستعادة وبوابة المندوب. حُذفت مساحة الاختبار السحابية بعد نجاحها. نجح أيضًا دخول miza وقراءة عشرة أقسام من التطبيق المتصل فعليًا بـSupabase وفحوص القاعدة الثلاثة عشر؛ انظر `application-verification.json`.

## التحقق الأمني

`server/test/security.mjs` يختبر الضيف، الموظف بلا صلاحيات، منح وسحب صلاحيات الجلسة، تعطيل الحساب، ملكية الملفات ومحاولة اجتياز المسار وعزل المندوب. يعمل ضمن smoke قبل اختبار تحديد معدل الدخول. `server/test/security-db.ts` يختبر RLS مباشرة على schema اختبار فقط: مندوبان متزامنان، منع إعادة الملكية، منع anon/authenticated، إعادة الدور بعد rollback. ملفات الاختبار لا تشغل على public. `security-verification.json` يسجل التحقق النهائي. لإعادة توليد السياسات شغل `node database/supabase/generate-rls.mjs`.
